# Python version floor/ceiling for this requirements file.
#
# The images are built `FROM python:3.10-slim`, and Dependabot has no other way
# to know that: a requirements.txt carries no `python_requires`, so it happily
# proposes releases that cannot install here. It did exactly that on 2026-08-27
# -- scipy 1.18.1 (needs >=3.12), scikit-image 0.26.0 and matplotlib 3.11.1 --
# and the ML build died at `pip wheel` with "No matching distribution found".
#
# With this file present Dependabot resolves against 3.10 and stops proposing
# the impossible. If the base image moves, move this with it.
#
# numpy is a second, independent ceiling and .python-version cannot express
# it. numpy is pinned at 1.26.4 because that is what the pinned torch 2.6.0
# was built against, and torch cannot move while mamba-ssm and causal-conv1d
# ship CUDA kernels compiled against it. So anything requiring numpy>=2 is
# out regardless of Python: opencv-python-headless stops at 4.11.0.86 here,
# not the 4.14 Dependabot offered, and pip fails the build outright rather
# than resolving around it. Check `requires_dist` for a numpy bound before
# raising any of the numeric pins below.
#
# Re-measured 2026-09-04 against PyPI metadata, because the ceiling is easy to
# mistake for a stale opinion and Dependabot re-proposes both every week:
#
#   opencv-python-headless 4.11.0.86  numpy>=1.21.2 ; python_version >= "3.10"
#   opencv-python-headless 4.12.0.88  numpy>=2,<2.3 ; python_version >= "3.9"
#   opencv-python-headless 4.14.0.94  numpy>=2      ; python_version >= "3.9"
#   ml_dtypes              0.5.4      numpy>=1.21.2 ; python_version >= "3.10"
#   ml_dtypes              0.6.0      numpy>=2.0.0
#
# 4.12.0.88's release notes say why: "Packages for Python 3.9+ are built with
# Numpy 2.x." So the wall is at opencv 4.12, not 4.14 -- there is no
# intermediate version to land on -- and it is a BUILD property of the wheel,
# not a bound someone can be talked out of. Both stay where they are until
# torch moves, which is what mamba-ssm and causal-conv1d gate.

# Core dependencies
# fastapi / starlette / prometheus-fastapi-instrumentator move as ONE set.
#
# The instrumentator's middleware runs before every endpoint and resolves the
# route name by walking `app.routes`. Up to and including 8.0.0 it does that
# with a bare attribute read:
#
#     File "prometheus_fastapi_instrumentator/routing.py", line 55
#       route_name = route.path
#     AttributeError: '_IncludedRouter' object has no attribute 'path'
#
# FastAPI 0.137.0 introduced `_IncludedRouter` and puts those objects in that
# list. Paired with an instrumentator <= 8.0.0 the service starts cleanly,
# answers /health 200 and pre-loads all five models -- then returns 500 on every
# POST to /api/v1/segment. Health stays green throughout, which is what makes
# the pairing dangerous rather than merely broken.
#
# 8.0.1 is the fix, not 8.0.0: it restructured resolution around
# `getattr(route, "path", None)` and skips what has none. Verified by reading
# routing.py in 6.1.0 / 7.1.0 / 8.0.0 / 8.0.1 -- the first three are identical
# on this line, so no smaller bump gets there.
#
#     fastapi 0.141.1  +  starlette 1.6.0  +  instrumentator 8.1.0
#
# starlette is a REPRODUCIBILITY pin, not a constraint: instrumentator 8.x
# already declares `starlette >=1.0.0,<2.0.0`, so pip would refuse a 0.4x
# resolve rather than accept one quietly. It is pinned because it is the member
# of the set nothing else in this file names, and an unpinned transitive floats
# on its own schedule. fastapi does not object -- 0.141.1 asks for
# `starlette >= 0.46.0` with no upper bound, so the 1.x floor comes entirely
# from the instrumentator.
#
# Verified against the running production service: all 9 models on one image
# plus sperm and microcapsule on another, 11/11 byte-identical outputs;
# /api/v1/batch-segment (the path the custom logging middleware special-cases)
# working; and /metrics still labelling `handler="/api/v1/segment"` correctly
# rather than degrading to "none", which is the failure mode a getattr-and-skip
# fix could plausibly have introduced.
fastapi==0.141.1

# transformers backs exactly TWO MODELS in this repo, and neither is
# microtubule any more:
#
#   models/segformer.py                 SegformerConfig / SegformerForSemanticSegmentation
#   sperm_final/models/backbone.py      Dinov2Model.from_pretrained("facebook/dinov2-large")
#
# There is a THIRD coupling that is not a model and is easy to miss:
# models/mamba_unet.py aliases the removed `GreedySearchDecoderOnlyOutput` /
# `SampleDecoderOnlyOutput` onto `transformers.generation.GenerateDecoderOnlyOutput`
# so `from mamba_ssm import Mamba` can finish importing. If that successor is ever
# renamed the shim RETURNS SILENTLY, the mamba import raises ImportError, and
# ml/model_loader.py drops Mamba-UNet out of the registry while /health stays
# green. So the probe must import models.mamba_unet too, not just the two
# checkpoints. (Present and correct at 5.15.1, checked 2026-09-04.)
#
# The old pin here was 4.57.1 for the microtubule v7 DINOv3 backbone, where
# 4.57.2 silently degraded the ViT features (303 real MTs -> 76 scattered, no
# error, no failed load). That reason is GONE: v5H (2026-08-17) replaced v7 with
# an nnU-Net whose checkpoint carries every weight, so MT imports no transformers
# and needs no HF_TOKEN. Only SegFormer and sperm still call `from_pretrained`.
#
# 5.5.4 was verified against BOTH survivors by loading their real checkpoints and
# hashing a fixed-input forward. Output is BIT-IDENTICAL to 4.57.1:
#
#   segformer (segformer_b0_spheroseg.pth)  sha 3527093be5a0632e
#   Dinov2Model facebook/dinov2-large       sha 15460fff556f45a6
#   sperm DINOv2Backbone layer_11/layer_17  sha a463aacc545d8f6c / 8cf462a9cdbfa640
#
# This clears 3 advisories (2 high, 1 medium) that are unfixed across ALL of
# 4.57.x. 5.5.4 needs only torch>=2.4, so it does NOT disturb the torch 2.6.0
# pin the mamba-ssm / causal-conv1d CUDA kernels are built against.
#
# CEILING, measured, not guessed: the SegFormer module layout was renamed and
# segformer_b0_spheroseg.pth stops load_state_dict-ing —
# `segformer.encoder.block.N.M`         -> `segformer.stages.N.blocks.M`
# `segformer.encoder.patch_embeddings.N`-> `segformer.stages.N.patch_embeddings`
# `attention.self.{query,key,value}`    -> `attention.{q,k,v}_proj`
# `attention.output.dense`              -> `attention.o_proj`
# `attention.self.sr`                   -> `attention.sequence_reduction.*`
# `layer_norm_{1,2}`                    -> `layernorm_{before,after}`
# `mlp.dense{1,2}`                      -> `mlp.fc{1,2}`
# `decode_head.linear_c.N`              -> `decode_head.linear_projections.N`
# The old note here said "5.16.1 breaks it, the break is above 5.6" — true, but
# seven minors too generous. Bisected 2026-09-04 against the real checkpoint on
# a seeded 1x3x1024x1024 input: 5.6.2 / 5.7.0 / 5.8.1 all reproduce the 5.5.4
# forward BIT-IDENTICALLY (sha ec4010afadd9a00d), and **5.9.0 is where it
# breaks** — 5.9.0, 5.11.0, 5.12.1, 5.13.1, 5.14.1, 5.15.0, 5.15.1 all fail.
#
# SECOND wall above that, and it is torch's, not ours: 5.10.1 / 5.10.2 / 5.10.4
# cannot even IMPORT a model on torch 2.6.0. `integrations/finegrained_fp8.py`
# evaluates `torch.float8_e8m0fnu` at module scope; 2.6.0 has no such dtype, so
# `from transformers import SegformerForSemanticSegmentation` raises
# ModuleNotFoundError. pip cannot warn about this — transformers declares
# `torch>=2.5` only under `extra == "torch"`, i.e. NO torch bound at all in a
# plain install. (5.11.0+ guards the attribute again and imports fine; they die
# on the rename instead.)
#
# So the SECURITY FLOOR and the working CEILING DO NOT OVERLAP, and that is why
# GHSA-xrqw-3rrv-vx5w / CVE-2026-9856 (high, `save_pretrained` path traversal)
# is left OPEN here. Its "first patched version" is 5.10.0 — which sits above
# the 5.9.0 wall, is itself YANKED from PyPI ("pushed from a week old main
# branch"), and whose unyanked siblings want a torch this stack cannot move to
# (mamba-ssm / causal-conv1d ship CUDA kernels source-built against 2.6.0+cu124).
# Every release at or above the fix was measured on 2026-09-04 and every one is
# unusable here — 5.10.x will not import, 5.11.0+ will not load the checkpoint.
# Moving torch off 2.6.0 is not on the table, so the pin STAYS.
#
# Leaving it open is safe because the advisory is UNREACHABLE here: it fires on
# `save_pretrained()` of a tokenizer or processor whose downloaded
# `chat_template` dict carries traversal keys. No Python under backend/ calls
# `save_pretrained()` at all, and the only two `from_pretrained` calls in the
# repo build a SegformerConfig and a Dinov2Model — no tokenizer, no processor,
# no chat template, and nothing is ever written back to disk.
# `backend/essays/tests/test_transformers_pin.py` asserts both halves so the
# reasoning cannot rot silently; the second one keys on the CLASS being loaded,
# because a tokenizer added to models/segformer.py would be just as dangerous as
# one added anywhere else.
#
# For the record, sperm is FINE all the way up: probed at 5.15.1, the
# `Dinov2Model.from_pretrained` load, the 2.5 GB Mask2Former checkpoint load,
# all four DINOv2 feature layers and pred_logits/pred_masks come out
# bit-identical to 5.5.4 (max|diff| 0.000e+00). SegFormer is the sole blocker.
#
# The only real fix is a key-remapping shim in models/segformer.py (or a
# re-exported checkpoint), verified against a real forward. Until someone writes
# that, do NOT "resolve" the alert by moving this number.
#
# dependabot.yml allows PATCH updates here and blocks minor/major. Re-run the
# probe — both checkpoints AND `import models.mamba_unet` — before crossing a
# minor, and note that CI cannot do it for you: the weights are not in the repo.
transformers==5.5.4

#
# onnx + onnx2torch move as ONE set with ml_dtypes, and the ORDER OF PINS HERE
# IS NOT WHAT MAKES IT RESOLVE -- pip resolves a requirements file as a set, so
# what makes numpy stay at 1.26.4 is the explicit `ml_dtypes` pin below, not
# where it sits in the file.
#
# The trap: `pip install onnx` on this image force-upgrades numpy 1.26.4 ->
# 2.2.6, which every numeric pin in this file is incompatible with (see the
# numpy ceiling at the top). The culprit is NOT onnx, which asks only for
# `numpy>=1.23.2`. It is onnx's own dependency `ml_dtypes>=0.5.4`, whose latest
# release 0.6.0 requires `numpy>=2.0.0` outright. ml_dtypes **0.5.4** satisfies
# onnx's floor exactly while still declaring `numpy>=1.21.2` on Python 3.10, so
# pinning it is the whole fix -- no onnx downgrade needed. Verified by resolving
# this file in a clean python:3.10-slim: numpy stays 1.26.4.
#
# onnx2torch is LOAD-BEARING, not a convenience. The four KymoButler graphs
# declare a STATIC [1,1,256,256] input, so onnxruntime rejects a 300x200
# kymograph outright; onnx2torch rebuilds the graph as an ordinary
# shape-agnostic torch nn.Module, which is the only reason arbitrary sizes run.
# It imports torchvision, so it must stay paired with the +cu124 torchvision
# above -- a PyPI torchvision against a +cu124 torch gives
# "operator torchvision::nms does not exist" at import.
#
# protobuf is a REPRODUCIBILITY pin, not a constraint: it is absent from the
# base image, arrives only as onnx's transitive, and onnx bounds it only from
# below (`>=4.25.1`). Nothing else in this file names it, so unpinned it would
# float on its own schedule.
